The most significant cross-component tension was between Section 2 (Extensibility Architecture Summary) and Section 1 (Copilot Studio Agent Architecture Summary). The financial modeling API only supports OAuth 2.0 client credentials, so the MCP connector authenticates as a service and the API cannot tell which consultant is asking, yet the Section 1 conversation flow originally let users supply client_id and engagement_id directly - meaning anyone who typed a valid ID could retrieve another engagement's valuation and breach the information barriers that SharePoint and Dynamics 365 enforce automatically everywhere else in the design. I resolved it by carrying the consultant's Entra identity through the A2A task object and a delegated sign-in to the MCP server, which now checks engagement-team membership in Dynamics 365 before it calls the API with client credentials. I also changed the Section 1 variable source so engagement IDs are selected from the user's own CRM engagements rather than typed, made denials return a generic "unauthorized" that never confirms an engagement exists, and logged every call by correlation ID for audit.
