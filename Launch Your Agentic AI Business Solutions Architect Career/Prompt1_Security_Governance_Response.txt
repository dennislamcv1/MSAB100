PROMPT 1: SECURITY AND GOVERNANCE NARRATIVE MATERIAL
Source artifact: Enterprise AI Strategy & Governance Playbook (GRL Corp), Fleet Logistics Router

Part A: Failure mode identification
The failure mode is a scope management gap that is also a trust boundary violation: the business asked for a Fleet Logistics Router with autonomous write access to the live production ERP routing database, so a single hallucinated route would have been executed against active drivers and created physical vehicle liability. I classified the request as Horizon 3 and enforced a downgrade to Horizon 1 before any budget was released: the agent runs in Azure AI Foundry as a read-only advisor that posts route suggestions to a human dispatcher in Teams, nothing is written to the database until the dispatcher approves it, and the boundary was logged at CoE intake with no exceptions permitted and carried into the instruction architecture and pilot design. This shows architectural judgment rather than platform knowledge because no platform setting flagged the risk; the decision was to move the trust boundary so the model never holds write authority, and to make that change at intake, when it cost nothing.

Part B: Engineering layer assessment
Guardrail friction is the strongest layer, because the Horizon 3-to-1 downgrade and the dispatcher approval gate are specific mechanisms, but I would reframe the enforcement: the Playbook puts the write prohibition in the system prompt, which prompt injection or model error can bypass, so the narrative needs the agent's managed identity to hold a read-only database role with no write grant on the routing tables. Metric trade-off is the weakest layer and is effectively absent, since the Playbook's thresholds (3,000ms latency, 30% thumbs-down, 20% week-over-week token spend) belong to the Warehouse Policy Desk; I would add dispatcher override rate and approval turnaround time as the Router's metrics and state the trade-off plainly: every route change now waits on a human, which slows dispatch, and that bounded delay is accepted against the unbounded cost of a wrong autonomous reroute. Deployment reality is partial (the CoE intake log and the Coder's validation of database boundaries and API security before provisioning are specified), so I would add a pre-production test that sends the agent adversarial and out-of-range routing requests and confirms zero writes reach the ERP, plus an audit log of every suggestion and approval decision so the human gate leaves evidence.

Part C: ROI quantification
The artifact supports one hard figure: the design removed the agent's only autonomous write path into the production routing database, so 100% of AI-generated route changes pass human approval before execution, and the Horizon 3 scope was rejected before any budget was allocated to it. The Playbook gives no fleet size, route volume, or incident cost, so I would estimate cost avoided as (AI route suggestions per month) x (dispatcher override rate during the Horizon 1 pilot) x (average cost of a misrouted vehicle: fuel, driver hours, missed-delivery penalties, and liability claims), drawing volume from GRL's dispatch logs and cost per incident from logistics finance or insurance claims data. The override rate is the credible input because the read-only design produces it: every suggestion a dispatcher rejects is a write the Horizon 3 version would have executed without review, so the pilot measures the exposure the design removed instead of relying on an assumed hallucination rate.
